## 1. Bugs

| # | Severity | Where | Problem | Fix |
|---|---|---|---|---|
| B1 | High | `payments/templates/pages/payment-success.html:15,27,29` | `redirect_to` from the query string is printed raw into an `href` and into a JS string. Frappe's Jinja env has no autoescape (`frappe/utils/jinja.py:65`), so `/payment-success?redirect_to=';alert(document.cookie);//` is reflected XSS on a guest page, and any URL is an open redirect. | Compute a safe `redirect_to` in `payment_success.py` (allow only `/path` or same-host URLs, else `/`), render with `{{ redirect_to \| e }}` in the href and `{{ redirect_to \| tojson }}` in the script. |
| B2 | Medium | `payments/templates/pages/payment-failed.html:12`, `payment-cancel.html:12` | Same raw `redirect_to` in an `href` (`javascript:` URLs, attribute breakout with `'`). | Same helper; add a small `payment_failed.py` context file (none exists today). |
| B3 | High (plausible, not reproduced) | `payments/payment_gateways/doctype/razorpay_settings/razorpay_settings.py:574-599` | Guest endpoint `order_payment_success` merges caller-supplied `params` into the Integration Request data (`integration_request.py:46-53`), then `authorize_payment` only checks that the given `razorpay_payment_id` is authorized/captured at Razorpay. It never checks the signature, the order id or the amount, and the caller can also overwrite `reference_doctype` / `reference_docname`. A buyer could reuse any captured payment id to mark a different, larger order as paid. | Verify `razorpay_signature` with `razorpay.Utility.verify_payment_signature` against the stored order id; only accept the three Razorpay keys from `params`; check amount and order id from the fetched payment. |

| B5 | Low | `payments/brand.py:13` | `app_email` is the placeholder `dev@paypilotlabs.com`. | Set the real support address. |
| B6 | Low | `payments/payment_gateways/doctype/mpesa_settings/test_mpesa_settings.py:8-11` | Unguarded `from erpnext...` imports: this test fails to import without ERP. Allowed by the independence check, so CI is green. | Skip the module when `erpnext` is not installed (`unittest.skipUnless`). |

## 4. Options

**A) Metadata only (low risk).** Change only what does not touch the bench app name:
- U1 `app_description`, U4 pyproject description, URLs, maintainers.
- U2 and U3 user-facing text.
- No npm packages exist, so nothing to rename there.
- Files: `pyproject.toml`, `payments/hooks.py`, `payments/utils/utils.py`, `paytm_settings.js`. 4 files, no other repo touched, no site migration.

**B) Full rename to `paypilotlabs_payments` (high risk).** Everything in A, plus N1-N5, N10, N12:
- Move `payments/` to `paypilotlabs_payments/`; rewrite imports and dotted paths in 34 files in this repo (all `.py` under the package, `hooks.py`, 6 JS files, `pyproject.toml`, `.gitignore`, `semgrep/`, `.github/workflows/ci.yml`, `.github/scripts/check_independence.py`, `brand.py`).
- Add a patch that renames `Installed Application` and `Module Def.app_name` rows on existing sites.
- Keep `/api/method/payments.*` callbacks working: leave a thin `payments` shim package or map every guest method in `override_whitelisted_methods`. A shim reintroduces a `payments` import name, which partly defeats the rename.
- Other repos, same day: ERP (`payment_request.py`, `utilities/__init__.py`, `templates/pages/order.py`, `test_order.py`, `docker/docker-compose.yml`), framework (`patches/v14_0/delete_payment_gateways.py`).
- Rebuild every ERP image; re-check every provider dashboard webhook.

**Recommendation: A.** The only thing B buys is a different internal name nobody outside devs sees, and it costs a 3-repo lockstep change, a site migration and a real chance of silently breaking payment webhooks. Fix B1-B3 in the same PR; they matter more than the name.
